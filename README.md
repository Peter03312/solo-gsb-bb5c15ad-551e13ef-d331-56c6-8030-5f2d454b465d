# 展馆应急疏散通行能力审核系统

面向展馆管理员的 Web 应用：录入各房间**待疏散人数**、有向**门 / 通道的单批次容量**以及**出口容量**，
系统按「所有房间同时撤离」的假设，基于网络最大流（Dinic）计算：

- **正常情况**下的最大可送达人数、总缺口及未满足人数的房间；
- **逐一封闭单个出口**时（封闭出口不能作为终点，其他通道与出口容量保持原值）的上述各项结果；
- 每个房间送达 / 缺口明细、各出口与各通道的实际占用量。

通道容量由各房间**共享**；同一个人在网络中只是一股流，跨多条通道天然**只计一次**。
方案比较规则：**先最大化总送达人数；总送达人数相同的方案，按房间编号顺序（自然序）优先满足编号靠前的房间。**
无路径到达任何出口的**孤立房间**无法获得流量，自动计入缺口。

技术栈：Node.js（Express）+ React（Vite）+ SQLite（better-sqlite3），容器一键启动。

---

## 一、一键启动（Docker Compose，推荐）

前置条件：已安装 Docker 与 Docker Compose 插件。

```bash
docker compose up -d --build
```

启动后：

- **访问地址：http://localhost:4000**
- 后端 API：`http://localhost:4000/api/...`
- 首次启动会自动安装依赖、创建 SQLite 数据库、建表，并写入一个「示例展馆 · 两层展区」示例方案。
- 数据库文件持久化在宿主机 `./data/evacuation.db`（容器内 `/data/evacuation.db`）。

停止 / 清理：

```bash
docker compose down          # 停止并删除容器（数据库保留在 ./data）
```

修改宿主机端口（默认映射 4000）：

```bash
HOST_PORT=8080 docker compose up -d --build   # 访问 http://localhost:8080
```
或在项目根目录创建 `.env` 文件写入 `HOST_PORT=8080`。

## 二、本地开发启动（不用 Docker）

需要 Node.js 20+。

```bash
# 1. 安装后端依赖（better-sqlite3 会使用预编译二进制）
npm install

# 2. 安装并构建前端
cd client && npm install && cd ..
npm run build:client

# 3. 启动服务（默认 http://localhost:4000，托管已构建前端）
npm start
```

前端热更新开发模式（两个终端）：

```bash
npm run dev:server   # 后端 http://localhost:4000
npm run dev:client   # 前端 http://localhost:5173 （/api 自动代理到 4000）
```

## 四、使用说明

1. 点击左侧「+ 新建」，填写方案名称；
2. 录入房间编号与待疏散人数；
3. 录入有向门 / 通道：选择起点房间、终点房间、类型（门 / 通道）与单批次容量；
4. 录入出口：出口编号、所在房间、出口容量；
5. 点击「保存并校验」。校验通过后自动展示审核结果：
   - **正常情况**卡片：需求总人数、最大可送达人数、总缺口、未满足房间列表与逐房间明细；
   - **逐一封闭单个出口**：每个出口一个折叠卡片，可展开查看封闭后的送达 / 缺口变化及出口、通道占用；
6. 可随时「修改方案」或删除方案。

房间编号排序采用自然序：例如 `R1 < R2 < R10`（含中文时按中文本地化顺序）。

## 五、输入校验规则（非法输入会被拒绝并说明中文原因）

以下情况接口返回 `400` 并给出明确原因：

- 方案名称为空；
- 房间列表为空、房间编号为空或重复；
- **待疏散人数为负数**或非整数；
- **门 / 通道容量或出口容量为负数**或非整数；
- 门 / 通道的**起点或终点引用了不存在的房间**；
- 出口**所在房间引用了不存在的房间**、出口编号重复；
- **方案没有任何出口**（或全部出口容量为 0）：任何人都无法撤离，直接拒绝；
- 方案名称与已有方案重名。

孤立房间（无论因未配置通道还是出口封闭导致无可达出口）不视为录入错误，但在结果中计入缺口。

## 六、算法说明

将疏散网络建模为有向容量网络：

```
超级源点 S --(待疏散人数)--> 房间 i
房间 a --(门/通道单批次容量)--> 房间 b     （有向，容量共享）
房间 i --(出口容量之和)--> 超级汇点 T
```

- `S→T` 最大流值即「最大可送达人数」，用 Dinic 算法求解；
- 同一人在流网络中只是一股流，经过任意多条通道都只在源边计一次，不存在重复计数；
- 封闭某出口时，直接不建立该出口到汇点的边（**封闭出口不能作为终点**），其余边容量保持原值后重新计算；
- 「同总量按房间编号优先」通过最大流后的**残量环流重路由**实现：按编号顺序逐房间在残量网络中向源点增广，
  增广路径只能借用编号更靠后房间已占有的源边流量，因此总送达人数不变、优先满足编号靠前的房间；
  已处理房间的源边流量会被锁定，不可被后续房间借走。

## 七、HTTP API 摘要

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `GET` | `/api/plans` | 方案列表 |
| `POST` | `/api/plans` | 新建方案（含完整房间 / 通道 / 出口数据，服务端校验） |
| `GET` | `/api/plans/:id` | 方案详情 |
| `PUT` | `/api/plans/:id` | 更新方案（全量替换房间 / 通道 / 出口） |
| `DELETE` | `/api/plans/:id` | 删除方案 |
| `GET` | `/api/plans/:id/analysis` | 审核结果：正常 + 逐一封闭每个出口 |
| `GET` | `/api/health` | 健康检查 |
